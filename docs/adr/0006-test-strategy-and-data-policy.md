# 6. Test strategy and data policy

Date: 2026-09-25

## Status

Accepted

## Context

- A query engine is only useful if its answers are right. Hand-written expected results are slow to write and easy
  to get wrong, and a small engine written partly by AI agents needs a harness that catches wrong answers, crashes
  and undefined behavior automatically on every PR.
- DuckDB reads the same Parquet files and has the semantics antb1 follows
  ([ADR 0004](0004-types-null-overflow-semantics.md)), so it can serve as an oracle.
- ClickBench's `hits` dataset is the first real workload. Its size (about 14 GB; 122 MB for the first partition)
  rules out committing it, and the maintainers decided that its values, query texts and published answers must not
  end up in the public repository or in public CI logs either.
- CI must be reproducible offline and must not flake.
- (2026-10-02) The 22 queries derived from TPC-H are the second workload. Their data, query texts and answers come
  from TPC's dbgen, which is licensed under the TPC End User License Agreement (EULA) v2.2. The only conda-forge
  package with it is `duckdb-extension-tpch`, an unsigned DuckDB extension.

## Decision

Test strategy:

- Layers: unit tests per module; integration tests; SQL logic tests whose expected results DuckDB writes (never
  edited by hand); oracle and seeded random differential tests against DuckDB; metamorphic tests; CLI goldens;
  harness self-tests (a deliberately wrong engine must be caught); parser fuzzing with a round-trip property; and
  ClickBench data tests. Each layer has a ctest label ([testing.md](../testing.md#labels)).
- DuckDB is a test dependency only and is never linked into `src/`. It runs locked down: one thread, no extension
  auto-install or auto-load, access limited to the fixture and data directories. The oracle never loads an
  extension; the one exception is the TPC-H-derived data generator below, a separate CLI process.
- Hermetic by default: no network except in tests labeled `data`, fixed seeds, single-threaded engine, fixtures
  generated by our own deterministic generator (integer arithmetic only, so they are byte-identical on Linux and
  macOS) or, for the data derived from TPC-H, by the pinned dbgen extension at test time.
- Sanitizers (ASan and UBSan), clang-tidy and a GCC compatibility build run on every PR; coverage floors per module
  only go up.
- Unsupported answers are counted, never silently skipped.

Data policy:

- Never committed: ClickBench Parquet files or samples, rows or values from them, ClickBench query text, result
  values (including DuckDB's published answers), or any file larger than 1 MiB. `pixi run lint` rejects Parquet and
  other data files and any file over 1 MiB; authors and reviewers check the rest.
- May be committed: pins (URL, sha256 and size of downloads), the hits-shaped schema used by our own fixture
  generator, our own queries, and per-query pass or fail status.
- The data is downloaded on demand, verified against the pin and cached outside the repository.
- Data tests always run redacted: a mismatch prints only the query number, column names and types, row counts, the
  first differing row index and hashes of both results, plus the local command to see details. CI never uploads data
  or results as artifacts.
- Ratchet: a committed status file lists the ClickBench queries verified to pass. A test fails on any unexpected
  pass or fail, and the PR that changes the pass set updates the file and the status table in
  [sql-subset.md](../sql-subset.md#clickbench-status) together.

Data policy for the data derived from TPC-H (amendment, 2026-10-02):

- **Source:** the conda-forge package `duckdb-extension-tpch`, locked at the same version and build as `libduckdb`.
  It contains TPC's dbgen under the TPC EULA v2.2. Installing the pixi environment, on a contributor's machine, an
  agent's or a hosted CI runner, installs it and accepts that EULA; the maintainers accepted this exposure, as DuckDB
  and DataFusion do. Correctness is judged by the live DuckDB oracle on the same files, never by TPC's official
  answers: the extension's text columns differ from the reference dbgen.
- **Never committed or pasted** (repository files, commit messages, PR and issue text, CI logs and artifacts): data at
  any scale factor; answer sets (TPC's, DuckDB's or ours); TPC tools and their data files (dbgen, qgen, the
  distribution file, query templates); query text in any dialect, fragments included; EXPLAIN output of those queries;
  text copied from the TPC-H specification. Queries are referred to by number (Q5) and the specification by clause.
- **May be committed:** pins; sha256 digests of the query texts the pinned package returns (a drift check); TPC-H
  table and column names and types; our own queries written from scratch; the per-query pass or fail ratchet with
  its status table.
- **Generation:** data, query texts and DuckDB's answers are generated at test time into the build tree
  (`build/<preset>/`) by a separate duckdb CLI process: started with `-unsigned -no-init`, one thread, extension
  auto-install and auto-load off, the pinned extension loaded by absolute path (DuckDB would search the home directory
  first), then locked down (allowed directories, no external access, configuration locked) before writing. The
  smoke test `harness.tpch.extension` checks that the extension loads.
- **Output:** TPC-H-derived tests run redacted like the data tests (query number, hashes and a local repro command)
  and print no timings in CI, whose logs and artifacts are public.
- **Naming:** public material says "derived from TPC-H" and carries this disclaimer verbatim: "This workload is
  derived from the TPC-H Benchmark and is not comparable to published TPC-H Benchmark results, as this implementation
  does not comply with all requirements of the TPC-H Benchmark." Numbers are per-query seconds and their geometric
  mean, never TPC metrics, never compared with official results, with the deviations and the machine listed. Before
  any number leaves the repository, the maintainers decide whether to ask the TPC for permission (TPC Policies
  8.1.4).

## Consequences

- Expected results come from an independent engine, so test authors do not have to compute answers by hand.
- Any semantic difference from DuckDB shows up as a failing test until it is fixed or registered as a divergence.
- The data tests cannot be reviewed by reading expected values in the repository; they rely on the live oracle and
  on redacted output instead.
- Contributors must run the data tests locally to see unredacted details of a mismatch.
- The status file and the docs table must change together, which the lint checks enforce.
- (2026-10-02) Every environment contains TPC's dbgen and its EULA applies to every installation. The
  TPC-H-derived tests depend on an unsigned extension and on the conda-forge build matching `libduckdb`; the
  extension and `libduckdb` must be updated together.
